# Layered city pilot

This read-only city uses the validated Physlib, pinned Mathlib and bridge snapshots. It includes every module in the `Physlib`, `PhyslibAlpha` and `QuantumInfo` roots, plus the Mathlib modules they explicitly import. Each building is a module, not a theorem. Physlib rises above the ground plane; Mathlib modules are arranged by their own source folders, with selectable surface markers and connections projected to the surface. Position is an overview aid, not evidence of declaration usage or mathematical similarity.

The initial radial overview groups source folders into labelled sectors and shows each file as an outer tile. The interior lines describe the folder hierarchy, not import or declaration edges. Selecting a sector opens its 3D district; selecting a file tile opens that file. The layer control switches the overview between Physlib-family roots and directly imported Mathlib files. Panning, pinch/zoom and keyboard sector selection are supported. The 3D scene is created on first drill-down, and its WebGL animation loop is paused while the overview is displayed.

The explorer uses actual source directory paths. The city picker groups files by their second-level source folder, such as `Physlib/QuantumMechanics`, and the different source roots remain separate. Each folder becomes a city containing neighbourhoods based on the next path component; their positions use a deterministic spiral packing. Files sit on small rotated grids inside their neighbourhoods. Selecting a folder focuses its area; selecting a file in the explorer or city updates both the selection and inspector. Drag or use two fingers on a precision trackpad to pan; pinch or use the zoom buttons to zoom. Right-drag turns within a limited range, and W/A/S/D also moves the camera. The default is a mostly top-down view at Medium quality. The Overview button frames the city, and Explore Mathlib below explicitly switches to the underground layer; selecting a Mathlib file also switches layers. Return to surface or Return to start restores the surface. Low, Medium and High quality adjust rendering resolution. Coloured ground and buildings identify folder cities; roads are decorative. This is a directory layout, not a mathematical clustering, dependency map or proof ordering.

Building height and basement depth increase logarithmically with the number of source lines, including comments and blank lines; this is not a measure of declaration count, quality or importance. Where a compatible declaration snapshot exists, up to 12 floors divide the recorded declarations evenly, so a floor can group several declarations. Otherwise, up to 12 source-range floors provide links to those lines and explicitly identify file-level imports. Neither source ranges nor imports establish declaration use. Select a building, then click a floor or choose it in the inspector to enter the floor explorer. Its draggable 3D interior is decorative and does not encode data. Declaration coverage is partial, and Mathlib declarations represent only linked pilot targets. These optional declaration snapshots are not currently produced by the publication workflow.

Physlib, PhyslibAlpha and QuantumInfo occupy separate labelled regions with coloured boundaries. The separation follows source roots; it does not imply isolation from one another.

The surface network shows explicit Physlib-family-to-Mathlib file imports in cyan. Imports within the Physlib family or within the included Mathlib subset are pink at the importer end and orange at the imported end. Selecting a building highlights its routes while softening the rest of the network. The underground view hides surface pipelines and Physlib buildings; it displays selected Mathlib-to-Mathlib routes below ground, while the inspector retains the full recorded import and importer lists. Up to three markers beside the building and matching inspector controls group edges into Mathlib pipelines, Physlib files it imports, and Physlib files importing it. These are relationship categories, not new graph nodes. Moving markers on highlighted routes are decorative and point in the recorded import direction. The pipeline toggle hides or reveals the network. A pipe represents a file import, not the use of a particular Mathlib result.

Select a building or file to show its direct imports within the displayed set. The inspector can switch between imports, importers, both directions or no selected file pipes. Pink pipes indicate what the selection imports; orange pipes indicate what imports it. At most 12 file pairs are highlighted at once; the displayed count reports the cap and the inspector lists all recorded relationships in the city. Mathlib pipelines are highlighted separately and are not subject to that limit. When optional declaration pilot data is present, selecting a declaration replaces selected file routes with dashed lines between displayed modules containing recorded declaration relationships; these are partial and may be routed. The inspector reports the number of displayed module pairs and lists recorded declarations, including those outside the displayed modules. No declaration-use or theorem-proof edge is inferred from a file import. District labels are capped and suppressed when they overlap; zoom or select a folder for more detail.

The browser uses Three.js and OrbitControls; bundling is performed by esbuild at build time. `npm ci && npm run build:city` generates the ignored `site/assets/city-bundle.js`, which the Pages workflow includes in its artifact. Run the local data and Mathlib build steps in the README first. For visual and interaction inspiration, see [Strata](https://github.com/themonk911/strata), whose source is not included here.

## Declaration extraction investigation

The existing [lean-vouch pilot](lean-vouch-pilot.md) records partial relationships for nine Euler–Lagrange declarations and does not cover most theorem-proof dependencies. The city does not reinterpret these records as complete.

Two other candidates are being compared against Physlib revision `4e2182f2b6f0a54207a2fa62002c264217f875d6`, its pinned Mathlib revision `56a005855ea17e0b0958f73ec801ae140b0a1679`, and Lean `v4.35.0`:

- [result-graph](https://github.com/PierreSenellart/result-graph) revision `2ee55ff6e521eabe71ecddac797e12f64448a5b6` built using the matching toolchain. Its default scope excludes dependency declarations; a pilot must pass `--include-prefix Mathlib.Analysis.Calculus` or another deliberate scope to include cross-library edges. Its source records edges from dependency to dependent, which must be normalized if adapted to this project's importer-to-dependency convention. Its default handling contracts excluded private/generated declarations, so apparent directness requires particular care.
- [lean-graph](https://github.com/aurasoph/lean-graph) revision `3bf57c70f0326e45b9e84345c8fe7cf520919358` pins Lean `v4.29.0`. Building its CLI with Physlib's `v4.35.0` and matching `Cli` dependency required experimental type annotations for three loop variables in the isolated research checkout. The modified tool is not a tested upstream release or a production dependency. Its output modes and filtering require separate evaluation.

Both extractors inspect elaborated information but make different choices about scope, compiler-generated declarations and filtered edges. Neither has yet been integrated into the publication pipeline. A production adapter must preserve the tool version, exact revisions, edge direction and kind, explicit versus contracted relationships, source-location semantics and coverage. It must be tested on known cross-library declarations before the UI calls an edge theorem usage.

### Local result-graph observation

An Euler–Lagrange extraction using `--root Physlib.ClassicalMechanics.EulerLagrange --include-prefix Mathlib.Analysis.Calculus` produced 3,581 nodes and 12,564 edges. Among them were nine Physlib declarations and 43 edges from a Mathlib calculus declaration to a Physlib declaration in result-graph's direction. For example, it reports a statement relationship from `ContDiff` to `ClassicalMechanics.euler_lagrange_varGradient`; the latter's source statement mentions `ContDiff`. Its value relationships may include theorem proofs or definition bodies, and default contraction can route edges through hidden declarations. These numbers are from one scoped run, not full Physlib or Mathlib coverage.

`scripts/adapt-result-city.mjs` converts the scoped output to an optional `site/data/city-declarations.json` that the city can show in the inspector when all snapshot revisions and toolchains match. The adapter checks the input hash, supported extractor revision, graph roots, module membership and declared scope. It does **not** run Lean or independently establish provenance: the caller supplies a provenance JSON with `physlibRevision`, `mathlibRevision`, `toolchain`, `extractorRevision`, `rawSha256`, `roots`, and `includedPrefixes`. For example:

```sh
node scripts/adapt-result-city.mjs raw.json site/data/graph.json site/data/mathlib.json provenance.json site/data/city-declarations.json
```

The file is ignored and not produced by the current Pages workflow. A missing, stale or incompatible pilot is not treated as evidence that the file contains no declarations. Automating a reproducible extractor wrapper, complete coverage tests and refresh strategy remains future work.

### Local lean-graph observation

The compatibility-adjusted CLI was run on the same Euler–Lagrange module with `--mode unified --readable --edge-types proof,sig`. It reported writing 210,684 nodes and 4,418,297 edges to a 356 MB NDJSON file, then exited unsuccessfully while attempting a further DOT/Graphviz output. All 210,684 lines in the file parsed as JSON, but the failed exit means the export must not be treated as a validated production artifact. The process reached at least 3.7 GB resident memory on this machine.

An inspection of the output found `ContDiff` as a signature relationship and `gradient` and `contDiff_id` as proof relationships of `ClassicalMechanics.euler_lagrange_varGradient`. It also found `gradient` in the signature of `ClassicalMechanics.eulerLagrangeOp_eq`. These observations agree in broad terms with the result-graph pilot, but different filters, edge semantics and possible routed relationships prevent a claim that their complete outputs are equivalent. Investigate the post-export failure and benchmark a smaller scope before considering automatic refresh.
